# 剧本格式 v2：自由主持与作者资料

本文描述当前的写作约定。`formatVersion: 2` 是数据格式版本，与内置剧本 `curtain-castle@2.1.1` 的内容版本不同。v1/v2 的已有存档继续使用各自冻结快照；导入结构和限额见[剧本格式](<adventure-format.md>)。

## 主持人与人物

- 一个主持 LLM 演绎旁白和所有人物。人物独立性来自各自的性格、职业能力、利益、知识与本局 cultivation 积累，不再要求每句对白或普通行动交给独立 agent 审批。
- 主持人可阅读全部作者资料、场景参考和角色卡，用于保持因果；**主持人知道不等于玩家和每个 NPC 都知道**。不能互相读心，也不能将私有资料当公开旁白逐字播放。
- 玩家决定自己的身份、感情、重大行动和立场。角色可以接受、拒绝、讨价还价或离开，不强迫恋情、服从或固定结局。缺点和误会不等于每时每刻没有常识。
- 普通说话、等待、清点、取物、交付和移动直接在正文推进，不等待动作工具或后台记录批准。已谈妥就自然完成，有真实冲突则写出具体拒绝或条件，不反复停在“准备”。
- 声明的战斗、检定及 HP 等数值仍由对应规则工具结算，不能由正文伪造骰点、抹去失败或重复发奖。不要把所有普通互动升级为检定。

## 三层信息

1. **世界常识**可放在 `dm.world`，主持人和合理具备该知识的角色可以使用，但不能凭常识认定一个人的具体身份。
2. **作者真相**放在 `dm` 的内部作者资料（例如 `authorTruth`、`knowledgeBoundaries`），交给主持人维持因果，注明哪些角色知道、误解或不知情。反转是可探索的事实，不是必须瞒到指定节拍的开关。
3. **角色个人认知**放在角色 `fields`，包括真实知识、误判、动机与底线；本局的新经历由 cultivation 累积。私有积累不自动展示在玩家面板，也不自动传给其他角色。

例如，内置剧本将“真正的吸血鬼晒太阳不死，只会变丑、声音嘶哑”作为世界常识；具体目标的真实种族属于作者与该角色自己的知识，其他人最初只有传闻。主持人知道真相，不必提前公布，也不得为了维持预设反转强迫角色对直接询问撒谎。公开资料、现场证据和有动机的对话均可提前改变剧情。

**可能直接显示在玩家界面的字段不能写未揭露秘密**：清单标题/描述、场景 `place/opening`、当前公开节拍、出口标签、检定标签和已公开的 `information`。程序投影可以防止直接返回内部字段，但模型保密表现仍需实际试玩，不能承诺绝不剧透。

## 兼容的场景结构

```yaml
# adventure.yaml 的场景参考；保留数据结构，不要求按图索骥
- id: study
  place: 书房
  opening: 雨声敲着窗，桌上放着一张图纸。
  cast: [bran, duke]
  beats:
    - id: arrival
      text: 壁炉里传来木柴的轻响。
      cue: duke
    - id: discussion
      text: 灯光落在图纸边缘。
  checks:
    - id: inspect
      label: 查看桌上的文件
      dc: 10
      bonus: 0
      successFlags: {document_read: true}
  information:
    - id: document-clue
      text: 文件上盖着一枚褪色的印章。
      requires: {document_read: true}
  exits:
    - to: hallway
      label: 离开书房
```

角色仍须在清单的 `characters` 列表声明并包含 `id/name/role/goal/fields`。`kind: world` 标记场景角色；省略或写 `party` 标记队友。`cast` 和 `cue` 供主持人参考并保持格式校验，不表示每个人必须轮流发言。

`beats`、`exits`、`requires`、`checks`、`encounter` 与 `information` 的数据结构继续保留，便于旧剧本、底层规则和导入校验兼容。它们不是普通叙事的行动审批表：主持人可根据上下文安排绕行、交涉、拒绝和新地点，不必逐拍推进或先调用转场工具。引用声明的检定和战斗时仍承接真实规则结果，后台记录器不能改写 flags、HP 或骰点。

正文可叙述新的细分地点，但后台只将已存在的场景 ID 写为剧本场景；新地点保存为叙事位置，不凭空创建剧本场景。进入已有场景时维护 visited 和已揭露信息，不额外触发独立 NPC 审批。到达 `ending` 参考场景不自动等于强制结束，应以正文确实结束为准。

## 正文先行，幕后整理

已提交正文是故事依据。幕后记录器只提取本轮已发生的物品总量、位置、重要事件和各 NPC 自己的实际言行/经历：

- 玩家愿望、假设、拒绝、未来计划与未满足的条件不能记为成功；未提及的物品不覆盖。
- 物品数量是确认的当前总量，不是可重复叠加的 delta；复用已有 ID，不凭相似字面猜别名。
- 每个角色只收到自己的亲历摘要。后来出场的人不能自动知道抵达前的经历，不把全篇正文复制到所有人的知识里。
- 记录事件幂等，格式失败不部分修改状态，也不抹去或改写已提交正文。面板可能滞后；后台失败不是人物拒绝，不重演已经完成的付款。

更多边界见[幕后养成](<npc-autonomy.md>)。

## 版本与测试

同一剧本 ID 和版本不能覆盖不同内容。升级示例必须递增内容版本，旧局仍读原快照，新内容只用于新开局，不自动迁移旧存档。

发布时由维护者统一执行 `npm run build:demo` 和测试。应检查：导入结构、兼容规则路线、主持提示包含作者资料但不强迫公布、初始公开 UI 不泄漏秘密，以及导入新版后旧存档快照未变。真实模型叙事质量和原 DSH Web 完整试玩仍需另行验收，单元测试不代表已验证线上体验。
