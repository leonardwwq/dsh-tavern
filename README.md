# DSH Tavern

### 让 AI 不止会聊天，还能主持一个世界。

**一款以 LLM 为叙事核心、以长期人物养成为驱动力的多角色互动冒险产品。**

把聊天窗口变成冒险现场：玩家自由行动，主持人承接故事，NPC 带着各自的欲望、立场和共同经历回应。一次选择不只换来一段回复，也为后续的人物关系与剧情留下新的起点。

> **不是让玩家适应系统认识的句式，而是让系统接住玩家想做的事。**

## 为什么做这个产品

文字冒险最吸引人的，不是菜单里有多少选项，而是那种感觉：**“我真的可以这么做，而且这个世界会作出反应。”**

LLM 让自由表达成为可能，但“能生成文字”距离“能玩”还有很长一段路：

- 玩家输入了一整段自然语言，系统却仍在等待某个标准答案。
- NPC 有丰富的人设，却只会轮流表态，像三位随叫随到的咨询顾问。
- 每轮都能写出新内容，但已经说定的事不断重谈，关系像没有发生过。
- 工程规则越补越多，故事反而越来越不敢往前走。

**DSH Tavern 探索的，是从“生成回复”到“持续主持一段可参与的经历”。**

它把自然语言行动、角色关系、剧情连续性和可靠存档放进同一个产品闭环，而不是把它们做成互不相干的功能按钮。

## 产品体验：从对话窗口到冒险现场

### 01 · 说出你想做的，而不是猜系统要你怎么说

玩家通过自然语言表达行动、态度与选择，系统理解上下文并推动过程发生，不要求使用固定指令或命中特定句式。

行动能否成功，应由世界情境、人物立场和选择后果决定，而不是由系统是否匹配到某种表达决定。自由不意味着所有愿望都能实现，而是每次表达都能获得有因果、有内容的回应。

**自然语言不只是输入方式，更应该是行动方式。**

### 02 · 同行的人物，不是会说话的选项

队友可以帮你，也可以有自己的算盘；可以赞同计划，也可以因职责、旧怨或利益提出不同选择。

人物的区别不止在于语气和头像，而在于：

- **想得到什么**：报酬、体面、认可、某个人的注意。
- **知道什么**：亲历、传闻、误解与尚未公开的秘密。
- **怎样办事**：先护人、先找侧门，还是先给自己找一个体面的理由。
- **记得什么**：你曾经做过的承诺、共同经历的风险，以及没有说开的矛盾。

### 03 · 关系不在这一轮结束，而在下一轮继续

借助 **cultivation 人物养成引擎**，NPC 各自积累记忆、关系、判断、心情和成长。

这些积累会重新进入主持上下文，成为后续演绎的依据：**不是只把经历存起来，而是让经历有机会改变人物下一次如何回应。**

亲密度不是服从按钮。接近一个人，不等于能够替他作决定；关系的价值来自持续相处，而不是把数值刷满。

### 04 · 内容可以更换，互动能力可以复用

世界背景、人物设定、场景和叙事风格由剧本资料组织，统一接入同一套主持、人物养成与存档机制。

产品不绑定某个故事、人物组合或固定结局。创作者提供处境、动机与冲突，玩家通过选择改变进程，LLM 负责承接情境，让内容成为可参与的经历，而不是只能依次阅读的分支树。

**剧本提供故事的起点，互动决定故事如何继续。**

## 产品洞察：自由输入，不等于自由行动

生成式交互的核心挑战，不是输入框是否开放，而是开放表达能否贯穿理解、过程和结果。

如果普通行为被拆成层层确认，人物的态度被直接升级成操作禁令，或幕后记录成为剧情继续的前提，那么即使玩家可以输入任何内容，体验依然是封闭的。

这不是增加更多关键词就能解决的问题，而是产品职责的划分：**记录系统应当维护故事连续性，而不是决定故事是否有资格发生。**

| 试玩暴露的问题 | 产品判断 | 对应设计 |
|---|---|---|
| 自由输入仍被固定句式卡住 | 交互自由必须贯穿结果，而不只停留在输入框 | 普通行动交给 LLM 理解与叙述，退出句式审批 |
| NPC 轮流表态，却没有事情发生 | 人物自主性应由行为和后果体现，而不是 agent 调用数量 | 一个主持人统一演绎，多个人物保留独立状态 |
| 故事要等所有后台工作完成 | 用户不应为系统内部的整理过程付出剧情等待成本 | 正文先提交，事实与人物养成在幕后处理 |
| 有人设，没有角色感 | 标签只有进入行动和关系才产生体验价值 | 用人物目标、主动行为和关系错位指导创作 |
| 有记忆，却像刚认识玩家 | 长期记忆的价值在于影响下一次交互 | 形成“经历—积累—读取—再回应”的闭环 |

**核心转变：从“让每个动作都获得批准”，转向“让每次选择都得到回应”。**

## 关键设计：把复杂度留给系统，把自由度交给玩家

### 一、一个叙事者，多个有状态的人物

前台由同一个 LLM 主持旁白、NPC 对话与剧情后果，减少多角色逐人决策造成的割裂和等待。

后台保留每个人物独立的记忆、关系和发展任务。**减少的是现场调度复杂度，不是人物的差异和长期积累。**

这是一次明确的产品取舍：不以多 agent 的数量证明先进，而以故事是否连贯、人物是否有区别来判断设计价值。

### 二、正文是发生过的故事，面板是故事的投影

背包、位置和纪事用于帮助理解世界，不充当普通行动的通行证。

```text
玩家表达行动
       ↓
LLM 主持：承接上下文，叙述过程与后果
       ↓
完整正文保存
       ↓
幕后事实整理 ──→ 物品 / 位置 / 重要事件
       ↓
cultivation 人物发展 ──→ 记忆 / 关系 / 信念 / 心情 / 成长
       ↓
进入后续主持上下文，支持下一轮互动
```

结构化记录服务于连续性，而不是把开放叙事重新收回规则表里。

### 三、把“失败体验”也设计成产品的一部分

后台整理暂时失败，不能被演成已发生的剧情被撤回，或人物无缘无故改变立场。

- **正文保留**：下一轮仍可承接已经发生的故事。
- **状态透明**：明确提示面板可能落后，不伪称记录成功。
- **重试有对象**：重新整理同一正文，不要求玩家重复已经完成的行动。
- **结果可去重**：重载、重试和迟到结果不能重复发物品或重复增加关系。
- **恢复有边界**：能恢复的依据原消息恢复，缺失的人物感知不靠猜测补写。

这不仅是异常处理，也是维护沉浸感和用户信任的体验设计。

### 四、确定性负责底线，生成式负责可能性

存档、所有权、幂等、并发和回滚由程序可靠处理；普通交谈、交付、移动和人物回应由 LLM 主持。

剧本声明的检定、战斗与生命恢复仍使用数值工具。**不是为了自由叙事抛弃工程可靠性，而是避免把工程可靠性误用成对每个普通动作的审批。**

### 五、让内容成为可迭代的产品资产

剧本以声明式 ZIP 包组织世界、场景和角色资料，支持版本管理、导入与冻结快照。

新剧本可以调整人物、节奏和体验重点；旧局继续保留原来的版本和共同经历，不因一次更新被悄悄重写。

## 从产品判断到可验证实现

这个项目的产品工作，不止于提出“做一个 AI 跑团”，而是把体验判断落进可运行、可复现的闭环：

**问题识别 → 体验目标 → 职责重构 → 功能落地 → 故障设计 → 对话验证 → 内容迭代。**

| 验证层次 | 已完成的工作 |
|---|---|
| 机制与工程 | 本次发布完整回归（2026-11-02）：tavern 183 项、cultivation 228 项通过，均无失败或跳过；包含真实 DSH Loader / Cordis 隔离集成 |
| 真实模型生成 | 覆盖付款、同义表达、等待、拒付、拒收离开、道歉后付款，并验证记录滞后时的后续叙事承接 |
| 生成结果回放 | 将模型生成的正文与提取结果送入实际运行时和存档链，验证失败保文、重载重试、旧物保留与不重复发钱；该组养成评价使用模拟模型 |
| 多轮人物积累 | 使用实际 cultivation 服务与模拟模型，验证双 NPC 分别积累记忆，成长与心情任务到期执行，更新结果进入后续主持上下文 |
| 内容迭代 | 剧本 2.1.1 小修及相关宿主链路 40 项测试通过，验证设定传递、导入与旧档兼容 |

这些结果证明了实现和特定链路，不替代长期游玩、人物趣味性或商业价值的验证。**当前成果是可运行的产品原型与经过迭代的核心机制，而不是虚构的用户增长或商业成绩。**

## 产品延展方向

在当前原型之上，可以继续探索三条产品化路径：

- **内容供给**：围绕统一剧本格式，扩展不同题材、人物组合与创作者工具。
- **关系驱动体验**：让共同经历成为复玩和人物发展的长期动力，而不只是一次性剧情消费。
- **体验与成本平衡**：优化后台任务触发、上下文预算和叙事节奏，让模型用量服务于可感知的体验收益。

以上是后续探索方向，不代表已经推出内容平台、形成付费模式或获得相关业务指标。

## 开始冒险

需要 Node.js 22+、DSH Web、可用的默认模型、`spawn` 服务及配套 cultivation。

```sh
dsh plugin --profile web add --workspace-root dsh-cultivation@^0.4.3 dsh-tavern-adventure@^0.3.0
```

将 `web` 替换为实际 profile，安装后重启原 DSH 进程并刷新原 Web 地址。

1. 在尚未发送消息的新会话中选择「地城冒险」。
2. 选择剧本版本，新建冒险，或明确接管已有存档。
3. 在主会话自由行动，通过面板查看生命、位置、物品与纪事。

普通旧会话不在中途换绑为游戏；接管后旧会话只读。玩法解释和剧情回顾可在局内进行，无关现实任务请另开普通会话。

## 开发与交付

```sh
# dsh-tavern 项目根目录
npm test
npm run check
npm run build:demo
node scripts/install-local.mjs --pack-only
```

两个项目可并列开发：tavern 消费 cultivation 服务，战役人物与日常角色库相互独立。本地开发能力需要配套打包、配套安装；发布时先发布 cultivation，再发布 tavern，确保声明的最低依赖可用。

安装、依赖来源核对及恢复说明见[开发文档](<docs/development-and-recovery.md>)。

### 当前版本与体验边界

- 当前版本：tavern `0.3.0`，依赖 cultivation `^0.4.3`；包含统一主持、正文后记录与幕后人物发展。
- 当前剧本源与示例 ZIP 为 `2.1.1`。发布不会自动更新运行中的 DSH 或替换旧局；旧局保持冻结快照。
- 当前采用简化 d20 遭遇，不是完整 D&D 5e，不提供完整职业、法术、先攻或多人联机。
- 人物演绎、视角区分与事实提取依赖模型；长期趣味性、稳定性、成本和原页面完整游玩尚需继续验证。
- 幕后任务仍消耗模型调用，面板可能短暂滞后；自动化测试与隔离模型实验不等于线上完整体验已验收。
- 安装成功、进程已加载、页面已刷新和实际试玩通过分别核验，不以其中一项替代其他项。

### 数据与隐私

存档默认保存在 DSH 主机的 `$DSH_HOME/tavern`（默认 `~/.dsh/tavern`），不是浏览器缓存，不提供云同步。在线模型会接收生成所需的剧情和人物上下文。

坏档不会自动清空。旧插件安装、冒险存档和日常角色库分别管理，不混用删除；不要删除存档或未知锁来绕过错误。详见[数据与恢复](<docs/development-and-recovery.md#本地数据与恢复>)。
